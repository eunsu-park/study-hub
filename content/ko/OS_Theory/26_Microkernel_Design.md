## 1. 모놀리식 vs 마이크로커널

### 1.1 아키텍처 비교

```
모놀리식 커널 (Linux, Windows NT 커널):
  ┌──────────────────────────────────────┐
  │              사용자 공간              │
  │   애플리케이션, 라이브러리, 데몬      │
  ├══════════════════════════════════════╡ ← 시스콜 경계
  │              커널 공간               │
  │  프로세스 관리 │ 메모리 관리 │ VFS   │
  │  네트워킹     │ 디바이스 드라이버     │
  │  파일 시스템  │ 보안    │ 암호화     │
  │  모두 하나의 주소 공간에             │
  └──────────────────────────────────────┘

  + 빠름 (커널 서비스에 IPC 불필요)
  + 컴포넌트 간 간단한 통신
  - 드라이버 버그 하나가 전체 커널 크래시 가능
  - 큰 신뢰 컴퓨팅 기반 (TCB)

마이크로커널 (L4, seL4, Minix 3):
  ┌────────────────────────────────────────┐
  │              사용자 공간               │
  │  앱  │ FS 서버  │ 네트 서버 │ 드라이버│
  │      │ (사용자) │ (사용자)  │ (사용자)│
  ├══════════════════════════════════════════╡
  │         마이크로커널 (~10K 라인)        │
  │  IPC │ 스케줄링 │ 메모리 (기본)       │
  └────────────────────────────────────────┘

  + 작은 TCB → 검증하기 쉬움, 더 안전
  + 드라이버 크래시가 커널을 크래시시키지 않음
  + 컴포넌트를 독립적으로 재시작 가능
  - 모든 커널 서비스 호출에 IPC 오버헤드
  - 더 복잡한 시스템 설계
```

### 1.2 코드 크기 비교

```
커널 코드 크기 (대략):

Linux 커널:       ~3천만 줄의 코드
Windows NT 커널:  ~5천만 줄
seL4 마이크로커널: ~10,000 줄의 C
L4 마이크로커널:   ~15,000 줄
Minix 3 커널:     ~6,000 줄

경험 법칙: 1,000줄당 1-25개의 버그
  Linux: 커널에 ~30,000 - 750,000개의 잠재적 버그
  seL4: 기능 사양에 버그가 없음이 수학적으로 증명됨
```

## 2. 마이크로커널 원칙

### 2.1 최소성 원칙

```
마이크로커널은 커널에 반드시 있어야 하는 메커니즘만 제공해야 함:

1. IPC (프로세스 간 통신):
   주소 공간을 넘나들기 때문에 커널에 있어야 함.

2. 스레드/프로세스 관리:
   컨텍스트 스위치에 특권이 필요하므로 커널에 있어야 함.

3. 주소 공간 관리:
   MMU를 관리하므로 커널에 있어야 함.

나머지는 모두 사용자 공간 서버:
  - 파일 시스템 → FS 서버 프로세스
  - 네트워크 스택 → 네트워크 서버 프로세스
  - 디바이스 드라이버 → 드라이버 프로세스
  - 메모리 정책 → 페이저 프로세스
```

### 2.2 기반으로서의 IPC

```c
/*
 * 마이크로커널에서 IPC는 핵심 작업.
 * 모든 것이 IPC를 통해 진행:
 *
 * 앱이 파일을 읽고 싶을 때:
 *   앱 ──IPC──▶ VFS 서버 ──IPC──▶ FS 서버 ──IPC──▶ 디스크 드라이버
 *                                                        │
 *   앱 ◀──IPC── VFS 서버 ◀──IPC── FS 서버 ◀──IPC──────┘
 *
 * 모놀리식 커널에서는 그냥:
 *   앱 ──시스콜──▶ VFS → FS → 드라이버 → VFS ──반환──▶ 앱
 *   (모두 커널 공간에서, IPC 불필요)
 *
 * 마이크로커널 IPC는 경쟁력을 갖추려면 빨라야 함.
 * L4 IPC: ~100 ns (Linux 시스콜의 ~50 ns 대비)
 */

/* L4 스타일 동기식 IPC 의사코드 */
typedef struct {
    unsigned long sender;
    unsigned long msg[64];  /* 메시지 레지스터 */
} ipc_message_t;

/* 메시지 전송 후 응답 대기 (call) */
int ipc_call(unsigned long dest, ipc_message_t *msg) {
    /* 목적지 스레드로 직접 제어 전달 */
    /* 커널은 중재만: capability 검증, 전환 */
    return 0;  /* 단순화 */
}

/* 메시지 대기 (receive) */
int ipc_recv(ipc_message_t *msg) {
    /* 메시지가 도착할 때까지 블록 */
    return 0;  /* 단순화 */
}
```

## 3. L4 마이크로커널 패밀리

### 3.1 L4 역사

```
L4 패밀리 트리:

L4 (1993, Jochen Liedtke):
  ├── 원본 손으로 작성한 어셈블리 구현
  ├── 마이크로커널 IPC가 빠를 수 있음을 증명
  └── IPC에 ~100 사이클 (Mach에서는 ~1000)

L4Ka::Pistachio (2001, 카를스루에 대학교):
  ├── 이식 가능한 C++ 구현
  └── 다중 아키텍처 지원

NICTA/UNSW L4 → OKL4 (상용, 수십억 대의 폰에 사용):
  └── Qualcomm 모뎀 펌웨어가 OKL4에서 실행

seL4 (2009, NICTA/UNSW):
  ├── 형식 검증됨 (정확성의 수학적 증명)
  ├── 능력 기반 보안
  └── 군사, 자동차, 항공우주에서 사용
```

## 4. seL4: 형식 검증된 커널

### 4.1 형식 검증의 의미

```
seL4의 검증이 증명하는 것:

1. 기능적 정확성:
   C 구현이 추상 사양을 올바르게 구현.
   "코드가 사양이 말하는 대로 동작한다."

2. 무결성:
   메모리 격리가 위반되지 않음.
   "프로세스 A가 프로세스 B의 메모리에 접근할 수 없다."

3. 기밀성:
   은밀 채널을 통해 정보가 유출되지 않음 (일부 제한 있음).

4. 최악 실행 시간:
   모든 커널 작업에 대한 한정된 실행 시간.
   "모든 시스콜이 X 마이크로초 내에 완료된다."

증명 체인:
  추상 사양 (Haskell)
       ↕ 동치 증명
  실행 가능한 사양 (Haskell)
       ↕ 동치 증명
  C 구현
       ↕ 동치 증명
  바이너리 (검증된 컴파일러 또는 변환 검증 통해)
```

### 4.2 seL4 Capabilities

```
seL4 능력 시스템:

모든 것이 능력(위조 불가능한 토큰)으로 제어됨:
  - 스레드 능력: 스레드 생성/관리
  - 메모리 능력: 페이지 매핑/해제
  - 엔드포인트 능력: IPC 메시지 전송/수신
  - 알림 능력: 비동기 시그널링
  - IRQ 능력: 인터럽트 처리

능력 작업:
  seL4_Call(ep_cap, msg)     메시지 전송, 응답 대기
  seL4_Send(ep_cap, msg)     메시지 전송, 대기 안 함
  seL4_Recv(ep_cap, msg)     메시지 대기
  seL4_Yield()               자발적으로 CPU 양보

보안 모델:
  능력이 없으면 작업을 수행할 수 없음.
  능력은 위임할 수 있지만 위조할 수 없음.
  커널이 모든 능력 작업을 중재.
```

## 5. 능력 기반 보안

### 5.1 능력 vs 접근 제어 목록

```
ACL (전통적):
  파일: /etc/shadow
  ACL:  root:rw, shadow-group:r
  확인: 요청하는 프로세스의 UID/GID가 ACL에 있는가?

  문제: "혼란된 대리인" 공격
  UID root인 프로그램이 /tmp/log만 필요한데
  실수로 /etc/shadow를 열어버림

능력:
  프로세스가 각 리소스에 접근하기 위한 명시적 능력을 가짐.
  open(/etc/shadow)은 /etc/shadow에 대한 FILE_CAP이 필요.
  프로세스가 그 능력을 부여받지 않았다면, 접근 거부.

  혼란된 대리인 해결: 프로세스는 명시적으로 부여받은
  능력만 가지며, 그 이상은 없음.
```

### 5.2 능력 구현

```c
/*
 * 단순화된 능력 기반 파일 시스템.
 */

typedef struct {
    int type;           /* CAPABILITY_FILE, CAPABILITY_DIR 등 */
    int object_id;      /* 이 능력이 참조하는 객체 */
    int permissions;    /* READ, WRITE, EXECUTE 등 */
    int delegatable;    /* 이 능력을 공유할 수 있는가? */
} capability_t;

typedef struct {
    capability_t caps[256];
    int n_caps;
} capability_space_t;

int cap_check(capability_space_t *cspace, int object_id, int perm) {
    for (int i = 0; i < cspace->n_caps; i++) {
        if (cspace->caps[i].object_id == object_id &&
            (cspace->caps[i].permissions & perm) == perm) {
            return 1;  /* 인가됨 */
        }
    }
    return 0;  /* 거부 */
}

int cap_delegate(capability_space_t *from, capability_space_t *to,
                 int cap_index, int new_perms) {
    capability_t *cap = &from->caps[cap_index];

    if (!cap->delegatable) return -1;
    if ((new_perms & cap->permissions) != new_perms) return -1;

    /* 같거나 더 적은 권한으로 새 능력 생성 */
    to->caps[to->n_caps] = *cap;
    to->caps[to->n_caps].permissions = new_perms;
    to->n_caps++;

    return 0;
}
```

## 6. IPC 성능

### 6.1 IPC 최적화 기법

```
마이크로커널 IPC를 빠르게 만들기:

1. 직접 프로세스 전환:
   송신자의 타임슬라이스가 수신자에게 전달.
   스케줄러 호출 불필요!

2. 레지스터 기반 메시지:
   짧은 메시지는 CPU 레지스터로 전달.
   작은 메시지에 메모리 복사 없음.

3. 지연 스케줄링:
   모든 IPC에 스케줄러 자료구조 업데이트 안 함.
   진짜 필요할 때만 업데이트.

4. 커널 진입/종료 최적화:
   레지스터 저장/복원 최소화.
   하드웨어 지원 사용 (SYSENTER/SYSCALL).

L4 IPC 벤치마크 결과:
  플랫폼            | IPC 지연 시간
  ------------------|-------------
  x86 (Pentium)     | ~100 사이클
  ARM (Cortex-A9)   | ~150 사이클
  x86-64 (현대)     | ~200 사이클

  비교:
  Linux 시스콜:       ~150-300 사이클
  Linux 파이프:       ~3000-5000 사이클
```

## 7. 하이브리드 접근법

### 7.1 실제 하이브리드 설계

```
순수하게 모놀리식이거나 마이크로커널인 시스템은 거의 없음:

macOS/iOS (XNU):
  Mach 마이크로커널 + BSD 모놀리식 레이어
  일부 서비스에 IPC 사용, 나머지에 직접 호출

Windows NT:
  하이브리드: 커널 모드 드라이버이지만 마이크로커널 같은 서브시스템
  Win32, POSIX 서브시스템이 사용자 모드 서버(원래)

Linux + KVM:
  모놀리식 커널이 하이퍼바이저 역할
  마이크로커널을 게스트로 호스팅 가능

QNX:
  자동차/의료용 진짜 마이크로커널
  사용자 공간의 드라이버, POSIX 호환

Fuchsia (Google):
  Zircon 마이크로커널
  능력 기반 보안
  대상: 폰, IoT, 노트북
```

## 8. 연습문제

### 연습문제 1: 마이크로커널 IPC 시뮬레이터

마이크로커널 IPC를 시뮬레이션하세요:
1. 파이프/소켓을 사용한 간단한 동기식 IPC 메커니즘 구현
2. "서버" 프로세스 생성: 파일 시스템, 메모리 관리자, 디바이스 드라이버
3. 모든 작업을 IPC를 통해 라우팅 (직접 함수 호출 없음)
4. 직접 함수 호출과 비교하여 IPC 오버헤드 측정
5. 메시지 배칭을 구현하고 개선 효과 측정

### 연습문제 2: 능력 시스템

능력 기반 접근 제어 시스템 구축:
1. 능력 구조 정의: 객체 ID, 권한, 위임 가능 여부
2. 구현: 생성, 확인, 위임, 취소 작업
3. 시나리오 생성: 최소 능력을 가진 웹 서버
4. 혼란된 대리인 공격이 방지됨을 보여주기
5. 전통적 ACL과 비교: 코드 복잡성과 보안

### 연습문제 3: 모놀리식 vs 마이크로커널 트레이드오프 분석

아키텍처 트레이드오프 분석:
1. 간단한 서비스를 (a) 라이브러리 호출, (b) IPC 기반 서버로 구현
2. 두 가지의 지연 시간과 처리량 측정
3. "드라이버 크래시" 시뮬레이션 - 마이크로커널은 복구하고 모놀리식은 안 됨을 보여주기
4. 어떤 IPC 비용에서 마이크로커널이 용납할 수 없게 되는지 계산
5. 분석 작성: 마이크로커널 vs 모놀리식을 언제 선택할 것인가

### 연습문제 4: 사용자 공간 디바이스 드라이버

사용자 공간에서 디바이스 드라이버 작성:
1. 데이터를 생산하는 가상 "디바이스" 생성
2. IPC를 통해 통신하는 사용자 공간 프로세스로 드라이버 작성
3. 비교를 위한 커널 공간 버전 작성
4. 측정: 지연 시간, 처리량, 신뢰성
