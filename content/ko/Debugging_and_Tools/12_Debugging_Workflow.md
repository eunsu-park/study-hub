# 종합 디버깅 워크플로우

**이전**: [디버깅을 위한 버전 관리](./11_Version_Control_for_Debugging.md)

## 학습 목표

이 레슨을 완료하면 다음을 할 수 있습니다:

1. 여러 디버깅 기법을 하나의 일관된 워크플로우로 결합하기
2. 재현-분리-수정-검증 사이클을 실제 버그에 적용하기
3. 심각도별로 버그를 분류하고 적절한 디버깅 깊이 선택하기
4. 체계적인 데이터 추적으로 데이터 처리 버그 디버깅하기
5. 경계를 분리하여 API 및 통합 버그 디버깅하기
6. 프로파일링 기반 최적화로 성능 버그 디버깅하기
7. 해결된 버그에서 배우는 사후 분석 프로세스 적용하기
8. 개인 디버깅 도구 모음과 체크리스트 구축하기

---

이 마지막 레슨은 지금까지 배운 모든 것을 한데 모읍니다: 에러 읽기, print 디버깅, 디버거, 버그 패턴, 전략, 로깅, 테스트, 린터, 타입 체킹, 프로파일링, 버전 관리. 실전 버그는 단일 범주에 깔끔하게 들어맞는 경우가 드뭅니다. 원인을 좁혀가며 여러 기법을 결합하고 도구를 전환해야 합니다. 이 레슨은 경험 많은 개발자들이 실전에서 버그에 어떻게 접근하는지 완전한 디버깅 케이스 스터디로 보여줍니다.

> **마스터 디버거:** 전문 디버거는 초보자보다 더 많은 도구를 아는 것이 아닙니다 -- 각 도구를 언제 사용하고 어떻게 효율적으로 전환하는지를 압니다.

---

## 1. 보편적 디버깅 워크플로우

모든 버그는 복잡도에 관계없이 이 사이클을 따릅니다:

```
┌──────────────────────────────────────────────────┐
│            디버깅 사이클                           │
│                                                   │
│   ┌─────────────┐                                │
│   │    재현     │  일관되게 발생시킬 수 있는가?    │
│   └──────┬──────┘                                │
│          ▼                                        │
│   ┌─────────────┐                                │
│   │    분리     │  무관한 코드를 벗겨내기          │
│   └──────┬──────┘                                │
│          ▼                                        │
│   ┌─────────────┐                                │
│   │  위치 파악   │  정확한 줄/값 찾기              │
│   └──────┬──────┘                                │
│          ▼                                        │
│   ┌─────────────┐                                │
│   │    이해     │  왜 잘못되는가?                  │
│   └──────┬──────┘                                │
│          ▼                                        │
│   ┌─────────────┐                                │
│   │    수정     │  코드 변경                      │
│   └──────┬──────┘                                │
│          ▼                                        │
│   ┌─────────────┐                                │
│   │    검증     │  수정 테스트, 회귀 테스트 추가,  │
│   └──────┬──────┘  부작용 확인                    │
│          ▼                                        │
│   ┌─────────────┐                                │
│   │    반성     │  이것에서 무엇을 배울 수 있는가? │
│   └─────────────┘                                │
└──────────────────────────────────────────────────┘
```

## 2. 케이스 스터디 1: 조용한 데이터 손상

### 시나리오

데이터 처리 스크립트가 CSV 파일을 읽고 요약 통계를 생성합니다. 사용자가 일부 데이터셋에서 평균 나이가 비합리적으로 높다(150+)고 보고합니다.

### 단계별 풀이

1. **재현**: 보고된 데이터셋으로 확인 -- 평균 나이 167.5 확인됨
2. **분리**: 최소 데이터로 테스트
3. **위치 파악 (print 디버깅)**:
```python
for row in reader:
    print(f"  age={row['age']!r}")
```
출력:
```
  age='30'
  age='25'
  age='1990'    # 나이가 아니라 출생 연도!
  age='28'
```

4. **근본 원인**: 일부 행에 나이(34) 대신 출생 연도(1990)가 포함됨
5. **수정**: 출생 연도를 감지하고 나이로 변환하는 `parse_age()` 함수 작성
6. **검증**: 정상, 출생 연도, 유효하지 않은 입력에 대한 테스트 작성

### 사용된 도구

1. **print 디버깅** -- 원본 데이터 값 확인
2. **repr()** -- 예기치 않은 데이터 형식 식별
3. **테스트** -- 수정 확인 및 회귀 방지

## 3. 케이스 스터디 2: 간헐적 크래시

### 시나리오

웹 API가 가끔 500 에러를 반환합니다. 대부분 정상이지만 예측 불가능하게 실패합니다.

### 풀이

로그에서 발견:
```
DEBUG: Found user: None
ERROR: 'NoneType' has no attribute 'get_profile'
```

**근본 원인**: 사용자가 존재하지 않을 때 `user`가 `None`인 상태에서 메서드 호출

**수정**: None 검사 추가, 404 반환

**예방**: 타입 힌트로 `-> User | None` 명시, mypy가 None 검사 누락을 잡도록

## 4. 케이스 스터디 3: 성능 저하

### 시나리오

보고서 생성 스크립트가 5초에서 2분으로 느려졌습니다.

### 풀이

cProfile로 프로파일링:
```
   ncalls  tottime
   100000    95.2   db.py:15(get_user_by_id)
```

**근본 원인**: N+1 쿼리 문제 -- 사용자당 하나씩 100,000번의 데이터베이스 쿼리

**수정**: 배치 쿼리로 변경하여 모든 사용자를 한 번에 로드, 딕셔너리로 매핑

**검증**: timeit으로 120초에서 4.8초로 개선 확인

## 5. 올바른 도구 선택

```
어떤 종류의 버그?
│
├─ 트레이스백이 있는 크래시?
│   └─ 에러 메시지 읽기 (1과)
│      그 다음: print 디버깅 또는 pdb 사용 (2-3과)
│
├─ 잘못된 출력 (크래시 없음)?
│   └─ print 디버깅으로 데이터 흐름 추적 (2과)
│      그 다음: 흔한 패턴 확인 (4과)
│      그 다음: 이진 탐색 디버깅 (5과)
│
├─ 간헐적 실패?
│   └─ 상태를 캡처하기 위해 로깅 추가 (6과)
│      그 다음: 재현하는 테스트 작성 (7과)
│
├─ "전에는 됐었는데"?
│   └─ git bisect로 깨뜨린 커밋 찾기 (11과)
│      그 다음: git diff로 변경 내용 확인
│
├─ 성능 저하?
│   └─ cProfile로 병목 찾기 (10과)
│      그 다음: timeit으로 해결책 비교
│
├─ 타입 관련 에러?
│   └─ 타입 힌트 추가하고 mypy 실행 (9과)
│
└─ 코드 스멜 / 스타일 문제?
    └─ ruff 실행 (8과)
```

## 6. 개인 디버깅 도구 모음 구축

### 필수 도구

```
□ Python 내장: breakpoint(), pdb, traceback
□ print 디버깅: !r이 있는 f-string, pprint
□ 로깅: 프로젝트에 맞게 설정된 logging 모듈
□ 테스트: pytest 설치 및 설정
□ 린팅: ruff (pylint, flake8, black, isort 대체)
□ 타입 체킹: pyproject.toml 설정이 있는 mypy
□ 프로파일링: cProfile, timeit, tracemalloc
□ 버전 관리: git (bisect, blame, diff, log)
```

### 개인 체크리스트

자주 만나는 버그를 기반으로 자신만의 디버깅 체크리스트를 만드세요:

```
나의 디버깅 체크리스트:
□ 에러 메시지를 꼼꼼히 읽기 (아래에서 위로)
□ 일관되게 재현할 수 있는가?
□ 최근에 무엇이 변경되었는가? (git log, git diff)
□ 알려진 버그 패턴인가? (off-by-one, None, 가변 기본값)
□ 크래시 지점에서 데이터가 어떻게 보이는가? (!r로 print)
□ 테스트 스위트가 여전히 통과하는가?
□ None을 확인했는가?
□ 타입을 확인했는가?
```

## 7. 디버깅 사후 분석

중요한 버그를 수정한 후에 물어보세요:

1. **근본 원인이 무엇이었는가?** (증상이 아닌)
2. **코드 리뷰를 어떻게 통과했는가?** (프로세스 문제?)
3. **테스트를 어떻게 통과했는가?** (커버리지 부족?)
4. **린터나 타입 체킹이 잡을 수 있었는가?**
5. **회귀를 방지하기 위해 어떤 테스트를 추가해야 하는가?**
6. **다른 곳에도 존재할 수 있는 패턴인가?** (유사한 버그 검색)

### 사후 분석 예시

```
## 버그: $1000 이상 주문에서 할인 계산 오류
날짜: 2024-01-20
심각도: 높음 (결제에 영향)
수정 시간: 2시간

### 근본 원인
커밋 def456에서 "코드 정리" 리팩토링 중 할인 임계값을
1000에서 100으로 변경. 매직 넘버 1000이 문서화되지 않아
리팩토링한 사람이 100이 맞다고 가정.

### 예방
1. 임계값 경계에 대한 단위 테스트 추가
2. 매직 넘버를 명명된 상수 LARGE_ORDER_THRESHOLD로 교체
3. 비즈니스 규칙을 설명하는 코드 주석 추가

### 교훈
매직 넘버는 항상 문서화된 명명된 상수여야 합니다.
```

## 8. 디버깅 마인드셋

### 체계적이되 영웅적이지 말 것

- 머릿속으로 해결하려 하지 말고 도구를 사용하세요
- 가정하지 말고 데이터로 검증하세요
- 증상을 쫓지 말고 근본 원인을 찾으세요
- 테스트를 건너뛰지 말고 회귀를 방지하세요

### 침착함 유지

- 버그는 정상입니다; 여러분의 능력에 대한 반영이 아닙니다
- 수정하는 모든 버그가 무언가를 가르쳐줍니다
- 최고의 개발자는 버그 없는 코드를 쓰는 사람이 아니라 버그를 효율적으로 찾고 고치는 사람입니다

| 트레이스백 읽기 | 크래시 에러 이해 | 1 |

| pdb / breakpoint() | 줄별 실행 분석 | 3 |
| 버그 패턴 인식 | 알려진 버그 유형 방지 | 4 |
| 과학적 디버깅 방법 | 체계적 버그 추적 | 5 |
| 로깅 | 프로덕션 진단 | 6 |
| 테스트 | 수정 확인, 회귀 방지 | 7 |
| 린터 (ruff) | 런타임 전 버그 잡기 | 8 |
| 타입 체킹 (mypy) | 타입 에러를 정적으로 잡기 | 9 |
| 프로파일링 (cProfile) | 성능 병목 찾기 | 10 |
| Git 도구 (bisect, blame) | 언제/누가 버그를 도입했는지 | 11 |

## 요약

- 실전 디버깅은 여러 도구와 기법을 결합
- 재현-분리-위치 파악-이해-수정-검증 사이클을 따를 것
- 버그 유형에 따라 올바른 도구 선택
- 개인 디버깅 도구 모음과 체크리스트 구축
- 사후 분석으로 버그에서 배우고 재발 방지
- 디버깅은 의도적 연습으로 향상되는 기술
- 목표는 버그를 수정하는 것만이 아니라 이해하고 유사한 것을 방지하는 것
