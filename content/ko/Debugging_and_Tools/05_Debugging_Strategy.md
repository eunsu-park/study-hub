## 학습 목표

이 레슨을 완료하면 다음을 할 수 있습니다:

1. 과학적 방법을 디버깅에 적용하기: 가설 수립, 테스트, 개선
2. 이진 탐색으로 대규모 코드베이스에서 효율적으로 버그 위치 파악하기
3. 버그를 분리하는 최소 재현 예제 만들기
4. 디버깅에서 상관관계와 인과관계 구분하기
5. 고무 오리 디버깅 기법으로 가정을 언어화하기
6. "증상에서 역추적" 전략 적용하기
7. 언제 휴식을 취하고 언제 도움을 요청할지 판단하기
8. 효과적인 소통을 위해 버그를 체계적으로 문서화하기

---

무작위 추측은 디버깅의 가장 느린 방법입니다. 전문 개발자들은 "뭔가 잘못됐다"에서 "찾아서 고쳤다"까지의 시간을 극적으로 줄이는 체계적 전략을 따릅니다. 이 레슨은 경험 많은 개발자들이 효율적으로 버그를 사냥하는 데 사용하는 사고 프레임워크와 기법을 가르칩니다.

> **핵심 통찰:** 디버깅은 수정법을 찾는 것이 아니라 **원인**을 찾는 것입니다. 원인을 진정으로 이해하면 수정법은 대개 자명합니다.

## 1. 디버깅을 위한 과학적 방법

디버깅은 근본적으로 과학적 과정입니다:

```
┌─────────────────────────────────────────────────┐
│           디버깅 과학적 방법                       │
├─────────────────────────────────────────────────┤
│                                                  │
│  1. 관찰       → 실제 동작이 무엇인가?            │
│       │                                          │
│       ▼                                          │
│  2. 가설 수립   → 무엇이 이를 일으킬 수 있는가?    │
│       │                                          │
│       ▼                                          │
│  3. 예측       → 가설이 맞다면 테스트할 때         │
│       │          무엇이 보여야 하는가?             │
│       │                                          │
│       ▼                                          │
│  4. 테스트     → 실험 실행                        │
│       │                                          │
│       ├─ 예측 맞음 → 가설이 맞을 가능성 높음      │
│       │   → 수정 시도                             │
│       │                                          │
│       └─ 예측 틀림 → 가설 수정                    │
│           → 2단계로 돌아가기                      │
│                                                  │
└─────────────────────────────────────────────────┘
```

### 실전 예제

**관찰**: "함수가 예상 합계 대신 0을 반환합니다."

**가설 1**: "입력 리스트가 비어 있을 수 있다."
- **테스트**: 계산 전에 `print(f"input: {numbers}")`를 추가.
- **결과**: 입력은 `[10, 20, 30]` -- 비어 있지 않음. 가설 기각.

**가설 2**: "누적 변수가 초기화되고 있을 수 있다."
- **테스트**: 루프 안에서 누적 변수를 출력.
- **결과**: 누적 변수가 0에 머묾. 발견 -- `+=`가 절대 실행되지 않는 `if` 블록 안에 있었음.

## 2. 이진 탐색 디버깅

코드가 크고 버그가 어딘가에 있을 때, 이진 탐색으로 O(log n) 시간에 찾을 수 있습니다.

### 2.1 기법

```
코드 블록: 100줄
│
├── 1-50줄:   여기서 확인/출력. 버그 있음? → 1-50줄에 버그
│   ├── 1-25줄:   여기서 확인. 버그 있음? → 1-25줄에 버그
│   │   └── ...정확한 줄까지 좁히기
│   └── 26-50줄:  1-25줄에 없음? → 여기에 있음
│
└── 51-100줄: 1-50줄에 없음? → 여기에 있음
```

### 2.2 실전 적용

```python
def complex_pipeline(data):
    step1 = clean_data(data)
    step2 = validate(step1)
    step3 = transform(step2)
    
    # 체크포인트: 이 시점에서 데이터가 올바른가?
    print(f"3단계 후: {step3!r}")
    # 올바르면 → 4-5단계에 버그
    # 틀리면  → 1-3단계에 버그
    
    step4 = aggregate(step3)
    step5 = format_output(step4)
    return step5
```

## 3. 최소 재현 예제 (MRE) 만들기

MRE는 버그를 여전히 재현하는 **가능한 가장 작은 코드**입니다. 이것이 가장 중요한 디버깅 기법입니다.

### 3.1 왜 MRE를 만드는가?

- 버그를 **이해**하도록 강제함 (만드는 과정에서 원인이 드러나는 경우가 많음)
- 근본 원인에서 주의를 분산시키는 무관한 코드를 제거
- 다른 사람에게 도움을 요청할 때 쉽게 **공유** 가능
- 전체 애플리케이션을 실행하지 않고 **수정을 빠르게 테스트** 가능

### 3.2 MRE 만드는 방법

```
전체 버그 코드에서 시작
          │
          ▼
한 번에 하나의 구성 요소 제거
          │
          ▼
   버그가 여전히 존재?
    ┌──────┴──────┐
    │             │
   예             아니오
    │             │
    ▼             ▼
계속 제거       되돌려 놓기;
               관련이 있음
    │
    ▼
더 이상 제거할 수 없을 때까지 반복
    │
    ▼
MRE 완성
```

## 4. 증상에서 역추적하기

코드를 위에서 아래로 읽는 대신, **잘못된 출력**에서 시작하여 역추적합니다.

### 4.1 과정

```
잘못된 출력
    │
    ▼
어떤 줄이 이 출력을 만드는가?
    │
    ▼
그 줄에 어떤 변수가 투입되는가?
    │
    ▼
그 변수들은 어디서 값을 받는가?
    │
    ▼
그 값들이 올바른가?
    ├── 예 → 결합 방식에 버그
    └── 아니오 → 더 뒤로 추적하여 잘못된 지점 찾기
```

## 5. 고무 오리 디버깅

코드를 무생물(고무 오리, 반려동물, 벽)에게 한 줄씩 설명하세요. 언어화하는 행위가 각 단계에 대해 명확하게 생각하도록 강제합니다.

### 5.1 방법

1. 책상에 고무 오리(또는 아무것이나)를 놓으세요
2. 코드가 **무엇을 해야 하는지** 설명하세요
3. 코드를 줄마다 따라가며 각 줄이 **실제로 무엇을 하는지** 설명하세요
4. "해야 하는 것"과 "실제로 하는 것"의 설명이 갈라지는 지점에서 버그를 찾은 것입니다

### 5.2 왜 효과적인가

- **정밀성을 강제**: 오리에게 손을 흔들며 넘어갈 수 없습니다
- **가정을 드러냄**: "이 줄이 카운터를 증가시키고... 잠깐, 정말 그런가?"
- **속도를 늦춤**: 훑어볼 때 버그가 숨고, 꼼꼼히 읽을 때 드러납니다

### 5.3 구조화된 자기 질문

오리가 없다면 스스로에게 다음을 물어보세요:

1. "이 줄에서 무엇이 일어나야 하는가?"
2. "실제로 무엇이 일어나는가?"
3. "내가 어떤 가정을 하고 있는가?"
4. "그 가정을 검증했는가?"
5. "동료에게 이 코드에 대해 무엇을 말할 것인가?"

## 6. 흔한 디버깅 안티패턴

### 6.1 산탄총 디버깅

**안티패턴**: 무작위로 이것저것 바꾸며 버그가 사라지기를 바라는 것.

**문제**: 우연히 수정을 찾더라도 버그를 이해하지 못합니다. 다시 나타나거나 새로운 문제를 일으킵니다.

### 6.2 도구 탓하기

**안티패턴**: "Python/라이브러리/OS에 버그가 있을 거야."

**현실**: 99.9%의 경우 버그는 여러분의 코드에 있습니다.

### 6.3 이해 없는 수정

**안티패턴**: Stack Overflow의 수정법을 왜 동작하는지 이해하지 않고 적용하는 것.

### 6.4 터널 비전

**안티패턴**: 같은 5줄을 한 시간 동안 응시하며 버그가 거기 있다고 확신하는 것.

**수정**: 한 걸음 물러나세요. 버그가 코드의 완전히 다른 부분에 있을 수 있습니다.

## 7. 휴식이 필요할 때

### 7.1 징후

- 진전 없이 같은 코드를 30분 이상 응시
- 명확한 가설 없이 변경을 가하고 있음
- 코드에 좌절하거나 화가 남
- 같은 줄을 계속 다시 읽음

### 7.2 대처법

- 15분간 자리를 떠나세요 (진지하게 -- 다른 일을 하세요)
- 문제를 누군가에게 설명하세요 (보내지 않을 메시지로도 좋음)
- 다른 작업으로 전환하고 나중에 돌아오세요
- 잠을 자세요 (무의식이 디버깅을 의식보다 잘합니다)

> **경험담:** 거의 모든 시니어 개발자는 버그에 몇 시간을 쓰고, 좌절하며 퇴근한 후, 다음 날 아침 5분 만에 해결한 이야기가 있습니다. 이것은 우연이 아닙니다 -- 맑은 눈이 지친 눈이 보지 못하는 것을 봅니다.

## 8. 도움 요청하기

### 8.1 요청 전에

1. 에러 메시지를 꼼꼼히 읽기
2. 에러 메시지를 온라인에서 검색
3. 최소 재현 예제 만들기
4. 이미 시도한 것 목록 작성
5. 문서 확인

### 8.2 좋은 버그 리포트 작성법

```
## 예상 동작
함수가 모든 양수의 합을 반환해야 합니다.

## 실제 동작
음수를 포함하는 입력에 대해 0을 반환합니다.

## 최소 재현 예제
```python
def sum_positive(numbers):
    total = 0
    for n in numbers:
        if n > 0:
            total += n
        else:
            return 0   # 버그: 건너뛰는 대신 즉시 반환
    return total

print(sum_positive([1, -2, 3]))  # 예상: 4, 결과: 0
`` `

## 시도한 것
- 입력이 올바른지 확인함
- print 문을 추가하여 실행 추적
- 함수가 첫 번째 음수에서 건너뛰지 않고 반환함

## 환경
Python 3.12, macOS 14.0
```

## 9. 디버깅 체크리스트

### 빠른 디버깅 체크리스트

```
□ 에러 메시지 읽기 (트레이스백은 아래에서 위로)
□ 에러에 언급된 정확한 줄 확인
□ 해당 줄에 들어가는 값 출력
□ 타입 확인 (int를 기대하는데 string이 아닌지?)
□ None 확인
□ 루프 경계 확인 (off-by-one?)
□ 최근 변경사항 확인 (마지막으로 뭘 바꿨지?)
```

### 체계적 디버깅 체크리스트

```
□ 버그를 일관되게 재현할 수 있는가?
□ 예상 동작 vs 실제 동작은 무엇인가?
□ 버그를 유발하는 최소 입력은?
□ 코드의 어디에서 동작이 예상과 달라지는가?
□ 최근에 무엇이 변경되었는가? (git diff, git log)
□ 잘못 처리되는 엣지 케이스가 있는가?
□ 잘못된 가정이 있는가?
```

## 10. 모든 것을 종합하기

모든 버그에 대한 디버깅 워크플로우:

```
1. 재현        일관되게 발생시킬 수 있는가?
       │
       ▼
2. 분리        MRE를 만들기. 최소 트리거는?
       │
       ▼
3. 위치 파악    이진 탐색 + 추적으로 정확한 줄 찾기
       │
       ▼
4. 이해        왜 이 줄이 잘못된 결과를 만드는가?
       │
       ▼
5. 수정        올바른 결과를 만들도록 코드 변경
       │
       ▼
6. 검증        수정이 동작하는가? 다른 것을 망가뜨리지 않는가?
       │
       ▼
7. 예방        이 버그가 다시 돌아오지 않도록 테스트 추가
```

## 요약

- 디버깅은 과학적 과정: 관찰, 가설 수립, 예측, 테스트
- 이진 탐색이 로그 시간에 버그 위치를 좁혀줌
- MRE 만들기가 가장 강력한 디버깅 기법 -- 만드는 과정에서 버그가 드러나는 경우가 많음
- 잘못된 출력에서 역추적하여 값이 잘못되는 지점 찾기
- 고무 오리 디버깅이 가정을 언어화(그리고 의문시)하도록 강제
- 안티패턴 피하기: 산탄총 디버깅, 도구 탓하기, 이해 없는 수정
- 휴식 취하기 -- 맑은 눈이 지친 눈이 놓치는 버그를 찾음
- 도움을 요청할 때 MRE와 시도한 것을 문서화하여 제공
